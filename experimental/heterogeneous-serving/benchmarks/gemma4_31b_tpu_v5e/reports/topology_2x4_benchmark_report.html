Gemma-4 31B Inference Benchmark on Cloud TPU v5e Topology 2x4 (TP=8)

Prefill, Decode & Multi-Step Serving Performance Analysis vs. Full Cluster (4x4, TP=16)

1. Executive Summary & Overview

This report provides the performance benchmark results for Gemma-4 31B (48 layers, hidden dimension 5,376, FFN intermediate dimension 21,504, 32 Q heads, 16 KV heads) running on a Cloud TPU v5e Topology 2x4 (2 hosts, 8 chips, TPU_TOPOLOGY="2x4", Tensor Parallelism TP=8).

The experiment was submitted and orchestrated using the official Ray SDK (JobSubmissionClient connecting to the KubeRay TPU cluster on GKE).

Key findings: 1. Prefill Throughput Advantage (+49.1% over TP=16): - Due to lower cross-host collective networking hops on the 2-host subslice (compared to the 4-host torus in TP=16), 48-layer step latency at $N=16,384$ tokens is compressed from 1,209.0 ms (TP=16) down to 810.8 ms (TP=8). - This delivers a peak prompt throughput of 20,206.4 prompt tok/s per 2x4 slice (50.82% Compute MFU), outperforming the 13,551.0 prompt tok/s achieved under TP=16. 2. Decode Concurrency & Multi-Step Saturation: - Single-step decode latency scales from 22.36 ms (BS=4) to 28.88 ms (BS=64) and 54.66 ms (BS=256), scaling up to 5,422.8 tok/s at BS=512. - In continuous multi-step generation (10 decode steps), generation throughput scales from 170.6 gen tok/s at BS=1 (TPOT = 5.86 ms/tok) up to 6,587.2 gen tok/s at BS=256 (TPOT = 38.86 ms/tok). 3. Long Context Scalability (BS=64): - Scaling context length from 128 to 4,096 tokens (up to 96 GB aggregate KV cache footprint) maintains steady step times (~28.7 to 29.5 ms) and ~2,200 tok/s decode throughput.

7. Summary Conclusions & Recommendations

  1. Topology 2x4 (TP=8) is Compute- & Communication-Optimal for Prefill: - In Gemma-4 31B, TP=8 provides twice the tensor dimension per chip ($d_{\text{local}} = 5376 / 8 = 672$) compared to TP=16 ($d_{\text{local}} = 336$), achieving higher GEMM matrix intensity. - Reducing the ICI ring from 4 hosts to 2 hosts cuts AllReduce ring synchronization overhead, delivering 20,206 prompt tok/s per slice.
  2. Decode Phase Saturation Dynamics: - For batch sizes $BS \le 32$, Decode latency is dominated by weight streaming and kernel launch overheads. - For $BS \ge 64$, KV cache retrieval from HBM becomes the active constraint.
  3. Disaggregated Serving Architecture: - Deploying 2x4 (TP=8) slices for Prefill workers and 4x4 (TP=16) slices for interactive Decode workers provides the best cost-to-throughput ratio.
